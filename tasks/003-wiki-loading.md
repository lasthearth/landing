# 003 — Wiki: загрузка статей, переходы между статьями, состояния «загружается»

Цель: пять багов загрузки публичной вики.
1. **После 50 статей вики ломается.** `WikiStoreService.load()` делает один `api.list()` (сервер отдаёт максимум 50) и не идёт по `next_page_token`. Страница статьи ищет статью только в этом снимке (`store.bySlug`), `loadBySlug` нигде не вызывается. С 51-й опубликованной статьи старые пропадут из списка, админки и очереди предложений, а по прямой ссылке будет «Статья не найдена».
2. **Переход по ссылке внутри статьи не меняет статью.** `wiki-article-view` ловит клики по `/…` и вызывает `router.navigateByUrl`. Маршрут тот же (`wiki/:slug`), Angular переиспользует компонент, а `WikiArticlePageComponent` читает slug из `snapshot` один раз. Адрес меняется, текст — нет.
3. **На каждом открытии статьи мелькает «Статья не найдена»**: пока данные грузятся, `article()` равен `null`, и шаблон сразу рисует пустое состояние. На странице списка так же мелькает «Статей пока нет».
4. **Очередь предложений обрезана на 50**: `WikiApiService.suggestions()` берёт одну страницу.
5. Почти все ссылки вики — `<a href>`: каждый клик перезагружает приложение. Это маскировало баг 2.

Ветка: agent/003 от agent/002 (если agent/002 уже влит в feat/wiki — от feat/wiki).

Правила проекта: AGENTS.md, перед работой — docs/API.md и docs/TRAPS.md. JSDoc на русском у каждого нового публичного элемента. Тексты — сразу ru и en через `npm run i18n -- set wiki <путь> "<текст>"`, в конце `npm run i18n -- check`.

Пути ниже — от `src/app/`.

## A. Хранилище: все страницы и одна загрузка за раз
`features/wiki/api/wiki-store.service.ts`:
1. `load()` идёт по страницам: `api.list({ pageToken })`, пока `next` не пустой. Предохранитель — 40 страниц (2000 статей); если он сработал — `console.warn` и выход с тем, что набралось. Снимок `byId` заменять один раз, в конце, а статьи, которые уже положил `put()` и которых нет в ответе, — не сохранять (их удалили или сняли с публикации).
2. Повторный вызов `load()`, пока идёт предыдущий, возвращает тот же промис (поле `inflight`). Сейчас список, статья и админка вызывают `load()` независимо.
3. Новый сигнал `public readonly loaded = signal(false)` — `true` после первой успешной загрузки. По нему страницы отличают «ещё не знаем» от «пусто».
4. Новый метод `refresh(id: string): Promise<WikiArticle | null>` — как `loadById`, но всегда идёт на сервер. Понадобится в задаче 004; здесь только добавить.
5. Комментарий над классом уже честный; убрать устаревшие упоминания localStorage в `routes/app.routes.ts` (строка ~49: «Пока без сервера — см. WikiStoreService») и в JSDoc `WikiArticlePageComponent`.

`entities/wiki/api/wiki.api.ts`:
6. `getBySlug(slug)` и `getById(id)` получают необязательный параметр `context?: HttpContext` и передают его в `http.get`. Иначе 404 по несуществующему адресу показывает глобальный алерт «Ресурс не найден» поверх собственного пустого состояния страницы (так устроен `errorInterceptor`, см. docs/API.md). Хранилище в `loadBySlug` / `loadById` / `refresh` передаёт `new HttpContext().set(SKIP_ERROR_ALERT, true)`.
7. `suggestions(status)` идёт по страницам так же, как `load()` (тот же предохранитель), и отдаёт склеенный список.

## B. Страница статьи
`features/wiki/ui/wiki-pages/wiki-article-page/`:
1. Slug — сигнал из `route.paramMap` (`toSignal`), а не `snapshot`.
2. Состояние — `signal<'loading' | 'ready' | 'not-found'>`, как в `features/news/ui/news-page/` (образец). На каждое изменение slug (`effect`, загрузка только в браузере — проверка `isPlatformBrowser`, как в остальных местах проекта):
   - `state = 'loading'`;
   - `await store.load()`;
   - если `store.bySlug(slug)` нет — `await store.loadBySlug(slug)` (черновик или статья за пределами снимка);
   - `state = article ? 'ready' : 'not-found'`;
   - при смене статьи — прокрутка к началу (`window.scrollTo({ top: 0 })`), если в адресе нет `#якоря`.
   Ответ на старый slug, пришедший после перехода на новый, не должен перетирать состояние: сверять slug перед записью.
3. Шаблон: `loading` — скелетон (`shared/ui/skeletons`, если подходящего нет — простой блок высотой с шапку статьи на токенах `--lh-*`); `ready` — как сейчас; `not-found` — как сейчас.
4. «К списку» и «Редактировать / Предложить правку» — `routerLink` вместо `href`. Признак `opening` и его спиннер оставить: чанк редактора всё ещё грузится после клика.

## C. Страница списка и админка
1. `wiki-list-page`: пока `!store.loaded() && store.loading()` — скелетоны карточек (3–6 штук, сетка та же), а не «Статей пока нет». Карточки статей — `routerLink` вместо `[attr.href]` (метод `articleLink` вернуть массивом или строкой для `routerLink`).
2. `wiki-admin-panel`: тот же признак для пустого состояния.
3. `wiki-article-view` — ссылки «См. также» (`[attr.href]="'/wiki/' + item.slug"`) не трогать: клики по ним уже перехватывает `onClick` и отправляет в роутер, а `href` нужен для открытия в новой вкладке.

## Проверка исполнителем
- `npm run verify`, `npx ng build` — 0 ошибок.
- Руками в `npm start` (бэкенд — dev-стенд из environment):
  1. открыть статью по прямой ссылке — нет вспышки «не найдена» и нет алерта;
  2. открыть несуществующий адрес `/wiki/net-takoy` — пустое состояние, алерта нет;
  3. в статье кликнуть ссылку `[[другая-статья]]` — меняются адрес и текст, страница наверху;
  4. «Назад» в браузере возвращает предыдущую статью;
  5. в Network при открытии статьи со списка — один запрос списка, а не два.
- Пагинацию на живых данных не проверить (статей меньше 50): временно поставить `MAX_PAGE_SIZE = 2` в `wiki.api.ts`, убедиться, что приходят все статьи и предложения, вернуть 50. В отчёте написать, что проверено так.

## Готово, когда
- 51-я статья открывается и видна в списке (проверено с `MAX_PAGE_SIZE = 2`);

- нет вспышки пустого состояния ни на списке, ни на статье.
